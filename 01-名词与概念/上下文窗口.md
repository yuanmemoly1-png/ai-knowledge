# 上下文窗口

## 什么是上下文窗口

上下文窗口（Context Window）是 [[LLM大语言模型]] **一次请求能处理的 [[Token与分词|Token]] 总量上限**——包括你发的所有消息（system + 历史对话 + 当前问题）和模型生成的回复，**输入输出加在一起**不能超过这个数。

可以把模型想象成一个只有一块白板的工作人员：白板写满了，再写新内容就必须擦掉旧的。白板之外的东西，它一概"看不见"。

## 为什么长对话会"遗忘"

模型本身**没有任何记忆**。你感觉它记得你三句话前说过什么，是因为每次请求时，客户端把**整段历史对话**重新发了一遍。当对话越来越长、逼近窗口上限时，常见两种处理：

1. **直接报错**：`context_length_exceeded`。
2. **静默截断**：自动丢弃最早的对话，模型"忘记"开头你说过的要求。

所以"遗忘"不是模型变笨，是旧内容被挤出了白板。

> [!warning] 常见误区
> 窗口标称 128K 不代表你能白用 128K。超长上下文会显著增加费用（按 token 计费），且很多模型存在"中间遗忘"现象——对塞在上下文中部的信息召回率明显下降，重要内容要放开头或结尾。

## 长上下文模型现状

| 模型 | 上下文窗口（约） |
| --- | --- |
| GPT-4o / GPT-4.1 | 128K ~ 1M |
| Claude 系列 | 200K |
| Gemini 系列 | 1M ~ 2M |
| DeepSeek 系列 | 64K ~ 128K |
| Qwen / Llama 开源系列 | 32K ~ 1M（视版本） |

窗口竞赛仍在继续，但"窗口大"不等于"用得好"——长上下文里检索关键信息的能力（所谓"大海捞针"测试）各模型差异很大。

## 上下文管理策略

长对话、长文档、Agent 多轮执行时，需要主动管理上下文。这是 [[记忆与上下文工程]] 的核心主题，常见策略：

### 1. 滑动窗口 + 摘要

只保留最近 N 轮原文，更早的对话让模型压缩成一段摘要：

```python
def build_messages(summary, recent_turns, new_question):
    """summary: 早期对话的摘要；recent_turns: 最近几轮原文"""
    messages = [{"role": "system", "content": f"以下是之前对话的摘要：{summary}"}]
    messages.extend(recent_turns[-6:])          # 只带最近 3 轮（一问一答为一轮）
    messages.append({"role": "user", "content": new_question})
    return messages
```

### 2. 重要信息结构化外置

把关键事实（用户偏好、任务状态）抽取成结构化数据存到外部，每轮只注入最新状态，而不是依赖模型从长对话里"记住"。

### 3. RAG 代替塞全文

与其把整本书塞进上下文，不如检索相关片段——见 [[RAG检索增强生成]]。这是对超长文档最经济的方式。

### 4. 子任务隔离

Agent 执行复杂任务时，给每个子任务开独立上下文，只把结论带回主对话，避免工具输出（网页全文、日志）撑爆窗口。

## 动手感受一下

```python
import tiktoken

enc = tiktoken.encoding_for_model("gpt-4o-mini")  # 128K 窗口
# 一篇 10 万汉字的中文文档大约多少 token？
text = "人工智能" * 25000  # 10 万字
print(f"token 数: {len(enc.encode(text)):,}")  # 约 15 万+，已经超窗
```

> [!tip] 经验法则
> 设计系统时先算账：你的 Prompt 模板 + 检索内容 + 历史对话 + 预期输出 ≈ 多少 token？留出 20% 余量再选模型档位。
