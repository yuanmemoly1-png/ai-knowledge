# 教材缺口增补（第二轮）—— 写作规范与大纲（契约）

本文件是「建议级四缺口」共 **4 节**的唯一契约。id / t / rel / qs 一律照抄，不得改动。

通用格式与《SPEC.md 第一部分》完全一致：`window.TB_SECTIONS = window.TB_SECTIONS || {}; Object.assign(...)`，每节含 `id / t / why / learn / body / keypoints / pitfalls / rel / qs / ev` 字段；**四节均不写 `from`**（无原书出处）。`body` 用模板字符串，代码块一律 `~~~` 围栏（禁止三反引号），无裸反引号，无 `${`。

`body` 固定四小节：
```
### 一句话说清      是什么 + 一个类比
### 展开讲          机制、关键做法；末尾加一句加粗的「和教材其它节的分工」
### 动手看          最小可跑代码 / 命令 / 改写示例
### 什么时候不该用   反模式 + 更简单的替代方案
```

篇幅：4 节全部为**完整节，body 500-800 汉字**。
语言红线：禁用「本节将介绍 / 如上文所述 / 详见笔记 / 综上所述 / 赋能 / 闭环」；`learn` 必须可检验。数字纪律：不确定的倍数/精度一律加「约」，不写具体跑分。

### 2.7 Git 协作：分支、PR 与冲突
- 分工句必须写明：**2.1 讲的是一个人的存档术（init/add/commit），本节讲一群人怎么协作**——2.1 是本节的前置
- 覆盖：分支为什么存在（隔离试验、并行开发）、`git switch -c` 建分支、`git log --oneline --graph` 看分支图；**完整协作环**：clone → 建分支 → 提交 → push → 发 PR → 评审 → merge；冲突怎么产生（两边改了同一行）、怎么解决（看标记、手动取舍、再提交）、怎么降低冲突频率（小步提交、常 pull）
- 常见翻车：直接在 main 上改、force push 覆盖别人的提交、忘记 pull 就 push
- 动手看：一个两条分支合并出冲突再解决的最小命令序列（可用 `git switch -c feature` → 两边改同一文件 → `git merge` → 编辑冲突标记 → `git add` → `git commit`）
- 不该用：一个人写的小项目，直接在 main 上提交完全可以；别为了仪式感套全流程

### 9.3 LoRA 与 PEFT 实操
- 分工句必须写明：**9.1 讲「什么时候值得微调」，本节讲「该微调的时候怎么做」**
- 覆盖：全参数微调的代价（动的是全部权重，显存与数据量都大）→ LoRA 的思路（**冻结原权重，只在旁边注入一对低秩矩阵**，原权重 + 小改动的和作为输出；只训新增的小矩阵，参数量少几个数量级）→ 为什么有效（微调改变的是低秩的「增量」）；QLoRA（把底座量化到 4bit 再挂 LoRA，消费级显卡就能跑）；PEFT 是实现这套的库
- 数据格式：指令对 / 对话格式，几十到几千条起步、质量远比数量重要
- 关键超参直觉：秩 r（改动的「容量」）、alpha（缩放）、挂载位置
- 动手看：transformers + peft 的最小代码骨架（`LoraConfig(r=..., task_type="CAUSAL_LM")` → `get_peft_model` → 训练），并注明「跑通优先，超参按官方示例」
- 不该用：模型缺知识（该上 RAG）、缺新行为范式（该改提示词）时先别微调；目标模型很小时 LoRA 收益有限
- **不得编造**：不写具体模型版本、不写具体准确率提升数字；`pip install peft` 这类命令可以写

### 8.12 实战：给 Agent 建一套评测集
- 分工句必须写清三层：**2.6 讲代码级测试（确定性断言）→ 8.9 讲评估维度与故障模式（理念）→ 21.5 讲生产监控（模式视角）；本节讲亲手做**——把前两者变成可运行的资产
- 覆盖四步循环：**① 建集**（从真实失败案例出发，不是拍脑袋造题；20-50 条起步；每条带「可判定的」预期：关键词命中 / 结构合法 / 要点覆盖）→ **② 跑**（同一份输入跑全部用例，记通过率，分维度统计）→ **③ 错误分析**（逐条看失败案例，归因到检索没中 / 提示词缺约束 / 模型能力不够，**改一处**）→ **④ 回归**（改完重跑全套，确认修好了且没改坏别的）
- LLM-as-judge：用强模型当裁判打分，必须给评分标准（rubric）而不是「打个分」；已知偏差要点名（偏长答案、偏自我风格），重要场景抽人复核
- 动手看：一个 ~20 行的评测脚本骨架（用例列表 + 逐条调用 + 关键词判定 + 通过率输出），能真跑
- 不该用：没有稳定输入输出的玩具项目不用建集；评测集建好就冻结不更新，会跟着产品一起烂掉

### 17.6 简历与项目包装
- 分工句必须写明：**14.3 讲作品三段论（客户问题→方案→结果）与 Demo，本节讲怎么把它压成简历上的几行字**——一个管「做出来」，一个管「写上去」
- 覆盖：AI 岗简历的结构判断（**项目经历是主体，技能清单是索引**）；一段项目的写法模板：一行说清做了什么（动宾结构）+ 一行技术要点（用什么解决什么）+ 一行结果（**必须有数字**）；**没有业务数据怎么量化**——用技术指标（评测通过率从 X 到 Y、时延、成本降幅）和规模数字（多少篇文档、多少条评测用例、多少次调用）
- 关键词对齐：简历里的词要能对上 JD 里的词（RAG / Agent / 评测 / 提示词），因为筛选第一关常是关键词匹配
- 动手看：给一组「改写前 vs 改写后」对照（改写前：「参与开发了一个 AI 知识库项目，负责后端」；改写后：动宾 + 技术 + 数字三行），这个对照要真实可用
- 雷区：堆名词不管深度（写了就要能答）、「精通/熟悉」滥用（写「用 X 做过 Y」更可信）、编造数据（追问两句就穿）、放截图不放可点链接
- 不该用：一页写不下就砍，别压字号；海投不改关键词等于没投
