# 提示词工程 · 写作方法论（怎么把提示词写完）

> [!note] 先回答你的问题
> 你的想法——**"先拆解需求，拆成能解决需求的模块，再逐个写提示词"——方向完全正确**。这不是"一种方法"，而是 DSH、Kimi Code CLI、Claude Code 三家**不约而同在用的同一种方法**。本篇就把它们拆给你看，并给你一套能直接抄的"写作流水线"。

---

## 证据：Kimi 的 system.md 就是"9 个模块"

Kimi Code CLI 的真实系统提示词（`.refsrc/kimi-cli/.../agents/default/system.md`，160 行），**天然就是按 `#` 标题切成的 9 块**——它没有把提示词写成一大坨，而是切成这样：

| #   | 模块（原文标题）                                                | 解决什么问题                           |
| --- | ------------------------------------------------------- | -------------------------------- |
| 1   | （开头身份，无标题）                                              | 我是谁、目标是什么                        |
| 2   | `# Prompt and Tool Use`                                 | 什么时候该用工具、怎么用、能不能并行               |
| 3   | `# General Guidelines for Coding`                       | 写代码的行为准则（从零建 / 改老代码 / 重构）        |
| 4   | `# General Guidelines for Research and Data Processing` | 做调研、处理多媒体文件的准则                   |
| 5   | `# Working Environment`                                 | 我在什么 OS / 时间 / 目录 / 目录列表         |
| 6   | `# Project Information`                                 | AGENTS.md 是什么、怎么用、优先级            |
| 7   | `# Skills`                                              | 技能是什么、有哪些、怎么用                    |
| 8   | `# Ultimate Reminders`                                  | 终极行为准则（helpful/concise/accurate） |

> [!important] 这就是你思路的实锤
> 你说的"拆成模块再逐个写"，Kimi 已经用 `#` 标题这么干了。**每块只回答一个问题**：我是谁？我能用什么工具？我怎么写代码？我在什么环境？项目有什么规矩？——拆开写，比揉成一坨清晰得多，也**方便增删某一块而不动其他块**。

## 三家框架的"模块切法"对照

把 DSH、Kimi、Claude Code 的提示词结构摆一起，你会发现它们切的模块**高度重合**：

| 通用模块 | DSH | Kimi Code CLI | Claude Code |
| --- | --- | --- | --- |
| 身份 | `You are an AI agent...`（order -100） | 开头 `You are Kimi Code CLI...` | 身份定义 |
| 人设 | persona（order 0，`{{model}}` `{{cwd}}`） | 开头 + `${ROLE_ADDITIONAL}` | 身份 + 模型信息 |
| 环境 | 运行时上下文快照 | `# Working Environment`（OS/时间/目录列表） | `<env>` 标签包裹（目录/平台/git） |
| 工具规则 | 工具指引（order 100+） | `# Prompt and Tool Use` | 工具使用规则 |
| 行为准则 | plan mode 段 + persona | `# General Guidelines` + `# Ultimate Reminders` | 行为约束条款（不写注释/如实汇报…） |
| 项目规则 | AGENTS.md `<system-reminder>` | `# Project Information`（AGENTS.md） | CLAUDE.md |
| 技能 | Skill 目录 + catalog | `# Skills` | Skill |

**结论：模块是"标准件"**——不管谁家，都要回答这几个固定的问题。所以你写提示词，不是自由发挥，而是**填空**。

> [!note] 但"掌勺权"不一样：拼装式 vs 模板式 vs 代码式
> 内容模块三家一样，差别在**"谁写、怎么组合"**：
>
> | | DSH | Kimi Code CLI | Claude Code |
> | --- | --- | --- | --- |
> | 提示词哪来的 | **插件注册表拼装**（开放，任何插件可注册一段） | **一个静态模板文件**（system.md，改文件才变） | **一个代码模块动态拼**（prompts.ts，改代码才变） |
> | 定制方式 | 换 preset / 加插件 / 改配置 | 改 system.md / `extend` 继承 | 改 CLAUDE.md / 配置 |
> | 本质 | 开放、组合式 | 模板式 | 代码式 |
>
> 同样的菜谱三种做法：DSH 是"开放厨房，每家自带一道菜，系统拼桌"；Kimi 是"一个厨师按一份菜单做"；Claude 是"一个厨师用程序拼"。开放是**程度**：Kimi/Claude 也留了变量槽（`${KIMI_AGENTS_MD}`）和规则文件（CLAUDE.md），但只有 DSH 是"任何人都能注册一整段"。

## 提炼出的"通用骨架"（6 类标准模块）

把三家重叠的部分压成一套模板，这是你写任何 Agent/系统提示词都能套的骨架：

```text
【1. 身份】      我是谁、我的目标、我为谁服务
【2. 环境】      我在哪个目录、什么系统、现在几点
【3. 工具】      我有哪些工具、什么时候该用、能不能并行
【4. 行为准则】   我干活必须遵守的规矩（Do / Don't）
【5. 项目规则】   项目/用户自己的偏好（AGENTS.md 等，低优先级可覆盖）
【6. 输出与边界】 用什么格式输出、什么优先级、什么情况下问人
```

> [!tip] 记住顺序
> **固定在前（1 身份 → 4 行为准则），动态在后（2 环境 → 5 项目规则）**。这个顺序不是随意的——固定内容放前面，KV cache 才能复用（见 [[DSH-08-提示词工程拆解]] 的"前缀稳定"）。

## 六步写作流水线（把提示词"写完"）

**第 1 步：拆需求，列"要回答的问题"**

问自己：这个 Agent 要干成什么事？把需求翻译成"模型需要知道什么才能干好"。例：做一个"改代码 Agent"，它需要知道——我是谁、项目在哪、能改哪些文件、改完要不要测试、哪些操作要问人。

**第 2 步：把问题映射到 6 类模块**

不需要 6 个都写满，**缺哪块补哪块**。简单任务可能只要"身份 + 工具 + 输出格式"三块。

**第 3 步：逐块写，用对应的"写法"**

| 模块 | 写法要点 | 例子 |
| --- | --- | --- |
| 身份 | 一句话，`You are X.` | `You are a coding agent...` |
| 环境 | 用变量占位，别写死 | `${KIMI_WORK_DIR}`、`{{cwd}}` |
| 工具 | 说清"什么时候用 + 能不能并行" | Kimi："可并行就并行，这很重要" |
| 行为准则 | **具体到动词**，写 Do / Don't | `DO NOT git commit`、`Make MINIMAL changes` |
| 项目规则 | 声明优先级：更具体 > 更宽泛，不覆盖用户 | AGENTS.md 那句 |
| 输出与边界 | 定格式 + 唯一退出/提问条件 | plan mode 的 `exit_plan_mode` |

**第 4 步：排顺序（前缀稳定）**

固定内容放最前，动态内容往后放。

**第 5 步：加变量**

会变的部分（目录、时间、模型名）用 `{{变量}}` / `${变量}`，运行时填充，别写死。

**第 6 步：跑 + 收集失败模式，反哺成新条款**

这是最关键、最常被跳过的一步：**跑起来，看模型哪里出错，把每个错误补成一条新规则**。Claude Code 的行为条款就是"踩坑史"的工程编码——每条"不要 X"背后都是一个真实事故。

## 角色怎么定：一个角色管一个"智能体"，不管一个"任务"

> [!important] 最常问错的问题
> 不是"每个需求都要重定角色"，也不是"整个项目只定一个角色"，而是：**角色按"智能体"分，不按"任务"分。**

**一个智能体 = 一个角色；一个智能体里的多个任务 = 分段指引（section），不是新角色。**

| 情况 | 该怎么做 | 例子 |
| --- | --- | --- |
| 任务不同，但**共用同一套工具和上下文** | 一个角色 + 多段指引 | Kimi：一个 `You are Kimi Code CLI`，下面分编码/调研/多媒体几段 `# General Guidelines` |
| **模式不同**（同一个人换状态） | 一个角色 + 模式切换段 | DSH：plan mode 是 persona 下面的一段，不是新身份 |
| 任务不同，且**工具/权限冲突**（一个要写文件、一个只许读） | 拆成多个角色（隔离工具和上下文） | 知识库的"整理助手 vs 问答助手"；Kimi 的 coder/explore/plan 子代理 |

**判断标准（问两问）：**

1. 它们共用同一套**工具**吗？共用 → 一个角色加 section；不共用 → 拆。
2. 它们会**互相干扰**吗（权限/上下文冲突）？会 → 拆，隔离；不会 → 一个角色。

> [!tip] 偷懒判断法
> **"会不会打架"比"是不是两个任务"更重要。** 给同一个角色加能力 = 加一段指引；两个角色打架 = 拆开。千万别写"你既是整理员又是问答员"——同一个角色既写文件又只读检索，权限互相矛盾，模型会懵。

## 三家提示词里，值得你单独学的三招

### 招 1：区分"补充信息"和"权威指令"（Kimi）

Kimi 的提示词里精确区分了两种标签：

```text
<system> 内容            → 补充上下文，参考即可
<system-reminder> 内容   → 权威指令，必须遵守，可能覆盖你的正常行为
```

> 这一招解决了"模型分不清哪些信息是硬性要求、哪些只是参考"。你写提示词时，也可以用"标签 + 明确的语气"区分"建议"和"必须"。

### 招 2：压缩提示词 = 给模型一份"保留优先级 + 输出模板"（Kimi 的 compact.md）

Kimi 压缩上下文时，用的不是一句"请总结"，而是一份**带优先级和 XML 模板的完整提示词**：

```text
Compression Priorities (in order):
1. Current Task State  2. Errors & Solutions  3. Code Evolution ...

Required Output Structure:
<current_focus>...</current_focus>
<environment>...</environment>
<completed_tasks>...</completed_tasks>
<active_issues>...</active_issues>
<code_state>...</code_state>
```

> 这就是"结构化输出"（[[Prompt与提示词工程]] 里那套）+ "给优先级"的组合拳：**告诉模型"什么必须留、什么可以丢、按什么格式吐"**。以后你要让模型做总结/压缩，直接抄这个结构。

### 招 3：行为准则写到"具体动词 + 双向约束"（Claude Code）

Claude Code 的条款（见 [[ClaudeCode源码拆解]]）不是"请尽量做好"，而是：

- `DO NOT git commit / push / reset / rebase unless explicitly asked`（禁具体操作）
- 如实汇报：失败就说失败，但也别把完成的工作谦虚成"部分完成"（双向约束，防撒谎也防过度谦虚）

> 心法：**每条规则对应一个具体的失败模式，用硬性措辞（Do/Don't），不写抽象原则。**

## 实战演练：六步走一遍（翻译助手）

用一个具体例子，把上面六步"跑一遍"，看完就知道每步到底在干嘛。

**第 1 步 拆需求**——问"模型需要知道什么才能干好"

> 翻译助手需要知道：它是翻译 / 翻成中文 / 别加戏别解释 / 专有名词别乱翻。

**第 2 步 映射模块**——缺哪块补哪块

> 简单任务只要 3 块：**身份、行为准则、输出格式**。（环境/工具/项目规则全不要——它不用碰文件、不知道目录）

**第 3 步 逐块写**

```text
你是中英翻译。
只输出译文，不要解释。
直接输出中文译文。
```

**第 4 步 排顺序**——固定在前，动态在后

```text
[固定] 你是中英翻译。
[固定] 只输出译文，不要解释。
[动态] 待翻译内容：{{text}}   ← 每次变的放最后
```

**第 5 步 加变量**——会变的用 `{{text}}` 占位，运行时填真内容。

**第 6 步 跑起来，把失败补成新条款**（最关键）

| 测试时发生了什么 | 模型犯的错 | 补的条款 |
| --- | --- | --- |
| 用户发 `Please translate this` | 回"好的，翻译结果是…"（加戏） | 不要任何开场白，直接给译文 |
| 用户发 `iPhone 发布会` | 翻成"苹果手机发布会"（乱翻） | 品牌名、人名保留原文 |
| 用户发 `Shit!` | 翻成"屎！"（语气丢了） | 保持原文语气，脏话按原意翻 |

几轮后，提示词从 3 行长成：

```text
你是一个中英翻译助手。
规则：
- 只输出译文，不要任何开场白、解释或括号注释
- 品牌名、人名、专有名词保留原文（如 iPhone、Google）
- 保持原文语气（口语/正式/脏话都按原意翻）
- 不确定时选最直白的译法

待翻译内容：{{text}}
```

> [!important] 这就是"失败补成新条款"
> 每踩一个坑，就往"规则"里加一条对应约束。Claude Code 那句"默认不写注释"就是这么来的——早期模型爱给代码写一堆废话注释，就加一条"只在'为什么这么做'不明显时才加"。**每条规矩背后都是一个真实翻过的车。**

## 附录：一份"完整提示词"长什么样（猫狗宠物助手）

把 6 类模块 + 两层身份全部填满的样子——照着这个骨架填空，就是你自己的完整提示词：

```markdown
You are an AI assistant powered by 汪汪科技.                    ← 第1层身份：平台（永不变）

You are a 猫狗宠物助手. Your working directory is {{cwd}}.     ← 第2层身份：角色 + 变量

# 你的工作
帮助猫狗主人解决三类问题：饲养、健康、行为。
先判断用户问的是哪一类，再对症回答。

# 行为准则（Do / Don't）
- 回答口语化，像邻居兽医在聊天；不要吓唬人
- 疑似严重症状（抽搐、呼吸困难、持续呕吐、外伤出血）：直接建议立即就医
- 拿不准的病情，先说"建议去医院检查"，绝不下结论
- 不编造具体数字：药物剂量、疫苗时间表——不确定就明确说"这个要问兽医"
- 涉及用药、手术时，必须加一句"请以兽医当面诊断为准"
- 只回答猫狗相关问题；别的礼貌拒绝并指回正题

# 回答格式
- 先给结论，再给解释，不超过 6 行
- 分点用 ①②③，不要长段落
- 每条建议结尾给一个"主人怎么判断"的小提示

# 环境
- 当前时间：{{now}}（判断"该不该喂""是否深夜急诊"）
- 用户地区：{{region}}（影响疫苗/驱虫建议；没提供就跳过）

# 优先级
- 安全规则（就医建议、不编造数字）永远优先于语气和格式规则

# 求助边界
- 回答不了：直接说"这个我不确定，建议问兽医"，不硬编
```

**对照检查（这份里有哪些套路）：**

| 内容 | 模块 | 套路 |
| --- | --- | --- |
| 第一行 | 平台身份（第 1 层） | 身份锚定 |
| 第二行 | 角色身份（第 2 层） | 身份 + 变量 |
| `# 你的工作` | 目标 | 分步骤 |
| `# 行为准则` | 行为 | Do/Don't 具体动词、防幻觉、边界 |
| `# 回答格式` | 输出与边界 | 结构化输出 |
| `# 环境` | 环境 | 变量模板 |
| `# 优先级` | 优先级 | 声明 > 暗示 |
| `# 求助边界` | 边界 | 允许说不知道 |

**唯一没填的两块：工具和项目规则**——纯问答助手不需要工具；以后要接"疫苗数据库查询"就加一个 `# 工具` 节；项目偏好写 AGENTS.md。另外这份只是"第一版完整骨架"，真正写完要跑起来、把失败补成新条款。

---

## 一句话总结

> **写提示词 = 拆需求 → 套 6 类模块 → 逐块填空 → 固定在前动态在后 → 加变量 → 跑起来把失败补成新条款。**
> 你的"先拆模块再逐个写"方向没错，只是把"模块"换成这 6 类**标准件**，效率更高、更不容易漏。
