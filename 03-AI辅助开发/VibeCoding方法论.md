# VibeCoding方法论

Vibe coding（凭感觉编程）是 2025 年流行起来的说法：你不再逐行写代码，而是用自然语言描述想要什么，让 AI 生成，跑一下看看效果，不行就再说一句让它改——全程「跟着感觉走」，靠对话迭代出软件。

## 什么是 vibe coding

传统编程的循环是「想清楚 → 写代码 → 调试」；vibe coding 的循环变成：

```text
描述意图 → AI 生成 → 运行看效果 → 不满意就继续说 → 满意为止
```

它的前提是 [[LLM大语言模型]] 已经强到能把一段中文需求直接变成可运行代码。开发者的角色从「写代码的人」变成「提需求、验收、修方向的人」。

> [!example] 一个典型 vibe coding 会话
> 「用 Python 写一个命令行记账工具，支持 add/列表/按月统计，数据存 SQLite」
> → AI 生成 → 跑起来发现统计不对 → 「月度统计把收入和支出分开显示」
> → AI 修改 → 再跑 → 对了，继续加功能。

## 适用边界：快与坑是一体两面

| 适合 vibe coding | 不适合 vibe coding |
| --- | --- |
| 个人小工具、脚本、爬虫 | 涉及钱、账号、隐私的系统 |
| 产品原型、Demo、验证想法 | 多人长期维护的大型项目核心模块 |
| 一次性数据处理任务 | 对性能/安全有硬要求的底层组件 |
| 学习练手、快速试错 | 需要逐行审计的合规代码 |

核心矛盾一句话：**原型阶段快得飞起，维护阶段可能债台高筑。** AI 生成的代码你可能根本没读过，三个月后自己都看不懂，一个小需求要动全身——这就是「vibe 债」。

> [!warning] 判断标准
> 问自己：「这个项目的代码，半年后还需要改吗？」需要改，就老老实实用下面的最佳实践约束 AI；一次性用完就扔，怎么快怎么来。

## 提示词驱动开发最佳实践

### 1. 小步迭代，一次只改一件事

❌「帮我把这个待办 App 做完，要有登录、列表、提醒、统计」
✅「先只做列表页：能添加待办、能标记完成」→ 跑通 →「再加删除功能」→ 跑通 →「再加截止日期」

每步都可验证、可回滚。一次要 10 个功能，AI 容易顾此失彼，出了错你也不知道是哪一步坏的。

### 2. git 版本控制是你的后悔药

vibe coding 最重要的纪律：**每完成一个小功能就 commit**。

```bash
git init                 # 项目第一天就初始化
git add -A && git commit -m "feat: 待办列表页"
# AI 改崩了？一键回到上一个好状态：
git checkout .
```

没有 git 的 vibe coding 等于裸奔——AI 一次错误重构就能毁掉你一下午的成果。

### 3. 让 AI 顺手写测试

每加一个功能都附带一句：「并写对应的 pytest 用例」。测试是 AI 产出的「验收单」：

```bash
# 每次大改后跑一遍，绿了就放心，红了就让 AI 修
pytest -x
```

有了测试兜底，后续「加新功能把旧功能改坏」这种 vibe 高发事故能少一大半。相关工具实操见 [[Cursor实战指南]]。

### 4. 先给上下文，再下指令

AI 不知道你的项目长什么样。改动前先喂背景：贴相关代码、用 `@` 引用文件、或在 rules/CLAUDE.md 里写好项目规范（见 [[ClaudeCode与终端Agent]]）。上下文越准，返工越少。

### 5. 关键代码亲自读一遍

账单计算、权限判断、SQL 语句、密钥处理——这些「错了代价大」的地方，AI 生成后逐行读，不懂就追问「这行是干嘛的」。这正是 [[幻觉Hallucination]] 风险最高的区域。

## 常见翻车场景与对策

| 翻车场景 | 症状 | 对策 |
| --- | --- | --- |
| 改 A 坏 B | 加了新功能，老功能默默挂掉 | 每功能配测试；大改后全量跑一遍 |
| 依赖幻觉 | AI 引用了不存在的库版本/API | 装依赖后先跑通最小示例再继续 |
| 无限修补 | 一个 bug 越修越歪，代码越改越乱 | 回滚到上个 commit，换思路重提需求 |
| 屎山膨胀 | 一个文件几千行，AI 自己都开始改错 | 主动要求「把 xxx 拆成独立模块」 |
| 密钥泄露 | AI 把 API Key 硬编码进代码并提交 | 用环境变量 + `.gitignore`；提交前 `git diff` 检查 |
| 环境玄学 | AI 给的安装命令在你机器上跑不通 | 把完整报错喂回去，别自己瞎猜着改 |

> [!tip] 黄金止损法则
> 同一个问题让 AI 修了 3 次还没好，立刻停下：回滚 → 把问题拆小 → 重新描述。继续在同一轮对话里纠缠，上下文越堆越乱，AI 只会越修越差。

## 心态：你是验收员，不是甩手掌柜

vibe coding 降低了「写」的门槛，但没有降低「负责」的门槛。能跑 ≠ 正确，正确 ≠ 可靠。把省下来的打字时间，花在想清楚需求和认真验收上，才是这套方法论的正确打开方式。
